# Go 1.26-1.27: Compatibilidade e manutenção

## Visão geral

O que muda para quem trabalha com módulos? O Go 1.26 renovou o `go fix`. No Go 1.27, o `go mod tidy` organiza melhor os requisitos e o `go test` ajuda a conferir se o código respeita a versão declarada no `go.mod`.

| Versão | Lançamento | Destaques para este material |
|--------|------------|-----------------------------|
| **1.26** | Fevereiro de 2026 | Modernização de código com `go fix` |
| **1.27** | Agosto de 2026 | Organização de `require`, checagem `stdversion` e documentação por versão |

Os exemplos desta página foram conferidos com **Go 1.27.1**.

## Go 1.26: modernizar o código

O `go fix` passou a usar o mesmo framework de análise do `go vet`. Ele oferece modernizadores para atualizar o código conforme a versão do Go usada pelo projeto.

```bash
# Ver as mudanças sugeridas
go fix -diff ./...

# Aplicar as mudanças
go fix ./...

# Conferir o resultado
go test ./...
```

O `-diff` retorna um status diferente de zero quando há mudanças sugeridas. Isso também permite usar o comando em verificações automatizadas.

Antes de aplicar, deixe as alterações do projeto versionadas e revise o diff. A intenção dos modernizadores é preservar o comportamento do programa.

No Go 1.27, as notas de lançamento registram novos modernizadores e mudanças nos nomes de analisadores. Confira os disponíveis no seu toolchain com `go tool fix help`, principalmente se scripts selecionam analisadores pelo nome.

Outra mudança do Go 1.26: `go tool doc` foi removido. Use `go doc`.

## Go 1.27: o que muda nos módulos

### Qual versão o `go mod init` escreve?

Com Go 1.27.1, um módulo novo começa assim:

```text
$ go mod init example.com/hello
go: creating new go.mod: module example.com/hello
$ cat go.mod
module example.com/hello

go 1.27.1
```

O comando usa a versão do toolchain que está sendo executado. `go work init` também parte dessa versão e leva em conta os requisitos dos módulos incluídos.

{% hint style="info" %}
As notas do Go 1.26 descrevem a escolha de uma versão anterior para módulos novos. Esse comportamento foi [revertido no Go 1.27](https://github.com/golang/go/commit/44ec057a3e89482cf775f5eaaf03b0b5fcab1fa4). Para escolher o mínimo do seu módulo, use `go get go@versão` e teste com a versão escolhida.
{% endhint %}

### `go mod tidy` organiza os blocos `require`

Se o módulo declara **`go 1.27` ou superior**, o `go mod tidy` reúne os requisitos em até dois blocos: um para dependências diretas e outro para indiretas.

Por exemplo, um arquivo que acumulou vários blocos:

```go
require (
    github.com/google/go-cmp v0.7.0
)

require (
    golang.org/x/text v0.23.0
)
```

Passa a ter um único bloco de dependências diretas, se o código importa pacotes dos dois módulos:

```go
require (
    github.com/google/go-cmp v0.7.0
    golang.org/x/text v0.23.0
)
```

```bash
# Conferir o que o tidy mudaria, sem editar os arquivos
go mod tidy -diff

# Aplicar e revisar
go mod tidy
git diff -- go.mod go.sum
```

O `-diff` já existe desde Go 1.23 e retorna um status diferente de zero quando há diferenças. A novidade do Go 1.27 é a consolidação dos blocos. Comentários são preservados, mas podem mudar de posição. Um módulo que ainda declara `go 1.26` mantém o comportamento anterior.

### `go test` confere a versão das APIs

O `go test` agora inclui o analisador **`stdversion`** entre as verificações de `go vet` executadas por padrão.

Imagine que seu `go.mod` declara `go 1.26.0`, mas o código usa `strings.CutLast`, adicionado no Go 1.27. Mesmo executando os testes com Go 1.27.1, a verificação aponta:

```text
strings.CutLast requires go1.27 or later (file is go1.26)
```

Você pode usar uma API disponível na versão mínima do projeto ou aumentar o requisito, se isso fizer sentido para quem usa o módulo:

```bash
go get go@1.27.0
go test ./...
```

Build tags também entram nessa análise. A checagem ajuda a encontrar incompatibilidades com a biblioteca padrão, mas continue testando com a versão mínima que o projeto promete suportar.

### Documentação de uma versão específica

Agora dá para consultar um pacote com `@versão`, sem trocar a dependência do projeto:

```bash
go doc github.com/google/go-cmp/cmp@v0.7.0 Equal
```

O comando pode baixar o módulo para o cache. Também ficou mais simples encontrar os exemplos executáveis da documentação:

```bash
# Listar os exemplos junto da documentação
go doc -ex bytes.Buffer

# Mostrar o código de um exemplo
go doc bytes.ExampleBuffer
```

Para abrir a documentação no navegador, use `go doc -http bytes`. A flag `-http`, disponível desde Go 1.25, é booleana.

### Diretivas `godebug` antigas

O Go 1.27 reconhece configurações `GODEBUG` removidas quando aparecem em diretivas `godebug` ou comentários `//go:debug`, desde que o valor seja o comportamento definitivo.

Por exemplo, `asynctimerchan=0` continua sendo aceito. Já `asynctimerchan=1`, que tentava restaurar o comportamento antigo dos canais de timers, causa erro nesses locais.

Se o projeto usa essas configurações, confira os valores antes de atualizar. Veja também a [documentação de GODEBUG](https://go.dev/doc/godebug).

### Fim do download direto via Bazaar

O comando `go` deixou de buscar módulos diretamente em repositórios **Bazaar (`bzr`)**. Isso afeta dependências que ainda precisam desse acesso. É necessário disponibilizá-las por um VCS suportado ou por um proxy de módulos que consiga servi-las.

Veja como controlar os VCS permitidos em [Security Features](../avancado/security-features.md).

## Atualizando um projeto

Primeiro, teste o código com o novo toolchain:

```bash
GOTOOLCHAIN=go1.27.1 go test ./...
```

Se o projeto vai passar a exigir Go 1.27, atualize o requisito e confira os arquivos:

```bash
go get go@1.27.0
go mod tidy
go test ./...
git diff -- go.mod go.sum
```

Em um workspace, você pode usar `go test work` para testar os pacotes de todos os módulos. Antes de publicar um módulo, entre no diretório dele e teste também com `GOWORK=off go test ./...`.

{% hint style="info" %}
Instalar Go 1.27 e exigir Go 1.27 no módulo são decisões diferentes. A diretiva `go` define o mínimo; `toolchain` sugere uma versão para trabalhar no projeto. Ela permite versões mais novas. Para executar com uma versão exata, use `GOTOOLCHAIN=go1.27.1`.
{% endhint %}
